# Требования

## Цель и пользователи

Detection engineer получает повторяемый пакет для одного наблюдаемого поведения; blue team проверяет телеметрию, преобразование полей и качество сигнала; purple team сопоставляет процедуру с правилом на разрешённом одноразовом стенде. Портфолио должно показывать инженерные артефакты и честные границы доказательств.

## Функциональные требования

1. Принимать ATT&CK technique ID и отказывать неизвестным/неоднозначным сценариям.
2. Генерировать собственное Sigma-правило с UUID, tags, logsource, экспериментальным статусом и false positives.
3. Парсить правило pySigma до конвертации; использовать реальные поддерживаемые backends и именованные pipelines.
4. Выдавать SPL и KQL раздельно с требованиями к модели данных. Не считать успешную конвертацию успешным запросом SIEM.
5. Читать локальный Atomic YAML, проверять technique ID, GUID и Windows-платформу, выдавать детали и план конкретного теста.
6. Не запускать команды; команда запуска появляется только при `--lab-ack`. Этот флаг подтверждает вывод команды, а не выполняет независимую проверку согласования.
7. Проверять положительные/отрицательные синтетические события в нормализованной модели и выдавать машиночитаемый отчёт.
8. Создавать пакет со SHA256 и отказывать перезаписи существующего каталога.

## Нефункциональные требования

Offline runtime; UTF-8; фиксированные зависимости и uv.lock; ограничение входа 8 MiB; безопасный YAML-loader; тестируемые ошибки с exit code 2; Windows/POSIX пути в инструкциях; отсутствие реальных логов и credentials в репозитории. Размер YAML ограничен, но загрузчик не является sandbox: для полностью недоверенных файлов нужен отдельный процесс с ограничениями памяти.

## Приёмка этапов

Offline MVP: все поддерживаемые техники преобразуются в оба backend; негативные данные отвергаются; wheel работает вне checkout; архив содержит полный контракт и lock. Это не означает лабораторную приёмку.

Лабораторная приёмка: для каждого сценария согласован один конкретный Atomic GUID, фиксирован upstream commit и SHA256 YAML, доказана доставка события в SIEM, запрос возвращает требуемый сигнал в заданном интервале и отрицательные случаи проверены на том же pipeline. Протокол заполняется по [LOCAL-PC.md](LOCAL-PC.md).

Общий готовый продукт: удалённый CI, чистая установка, наблюдаемые результаты стенда, воспроизводимые инструкции и проверенные release assets. Состояние отмечается в [VERIFICATION.md](VERIFICATION.md).
